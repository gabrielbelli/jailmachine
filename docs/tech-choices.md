# Current technology choices (not architecture)

These are implementations of the ADR interfaces as of 2026-09-14. Swap them
without touching the ADRs.

| Interface (ADR) | Current choice | Why / notes |
|---|---|---|
| Host client language | Go (cobra) | Single binary; same ecosystem as podman/gvproxy |
| Backend, macOS (0002) | QEMU + HVF, `-M virt`, EDK2 pflash, QMP | Apple Virtualization.framework/vfkit **cannot boot FreeBSD/arm64** (kernel dies after loader; no UART either) — verified 2026-08-20 and by independent reports |
| Backend, Linux (0002) | QEMU + KVM (planned) | Same argv, different accel |
| Hypervisor launch (0002) | QEMU **without `-daemonize`**, launched like every detached helper (gvproxy, the `ssh -N -L` forward, forwarder, resolver, sleeper, `jm _wake`) through a `/bin/sh` intermediate that backgrounds it and exits, with `Setsid`, so it is reparented to launchd (`internal/procx`); `-pidfile` kept; readiness is the pid file plus a QMP `query-status` answer (`prelaunch` or `running`) within 15 s, and an early exit reports the tail of `qemu.log`. Console is `-chardev file,…,append=on -serial chardev:jmcon`, and a cold start truncates `console.log` itself. The exact argv is saved to `qemu.argv` at every launch | Under HVF, saving GIC state initialises Objective-C classes in Hypervisor.framework, and `-daemonize` forks without exec, so `migrate` aborts with SIGABRT (`_objc_fatal performForkChildInitialize`), measured 2026-09-13. The intermediate stops a helper becoming a zombie of a wrapper that execs podman or docker. Verified 2026-09-14 on a cloned machine: every helper reparented to pid 1, `jm stop` clean. A machine whose QEMU is still daemonized reports `hypervisor was started by an older jm` until it is restarted once |
| Guest (0003) | FreeBSD 15.x arm64, ZFS, `podman-suite` + `ocijail`, `bastille`, `pf`, `linux` compat | 15.x kernel needed to run 15.x userlands in jails/containers. Linuxulator UDP is sound — bind, send, receive, DNS and `/udp` publishing all verified — with one known syscall-semantics gap: a **zero-length** `recvmsg()` on a datagram socket returns at once (FreeBSD's own behaviour, shared with macOS) where Linux blocks until a datagram fills `msg_name`. busybox's `nc -u -l` depends on the Linux behaviour and dies with `EAFNOSUPPORT`; every other UDP server is unaffected. A fix belongs in FreeBSD's `linux_recvmsg`, not in jm |
| Seed format (0003) | NoCloud ISO, label `cidata`, `#!/bin/sh` user-data | Consumed by `nuageinit` in the official `BASIC-CLOUDINIT` images |
| File sharing (0007) | QEMU `virtio-9p-pci` + `-fsdev local,security_model=mapped-xattr,multidevs=remap` (`$JM_9P_SECURITY` overrides at `jm start`), one pair per share with a **pinned PCI `addr=`**; guest `p9fs` (autoloaded by devmatch) mounted from `/etc/fstab` with `late,failok` | `mapped-xattr` since 2026-08-21 (ADR 0007 amendment): `none` applies the guest's modes to the host file, and the host end of the share is the unprivileged Mac user, so a container running as root could not rewrite a file it had just made read-only and `git clone` into a share failed on its pack temp files. `mapped-xattr` keeps guest ownership and modes in `user.virtfs.*` xattrs, which costs only host-side cosmetics — a container-created file reads as `0600` on the Mac. `$JM_9P_SECURITY` takes `none` or `mapped-file` for the other trade. An unpinned `addr=` shifts the disks' PCI slots, invalidates the EFI boot entry and the firmware then deletes it for good. Known gaps: `utimes` is a silent no-op, no `inotify` events reach the guest (issue #4, polling watchers work), ~70 MB/s, and metadata much slower still (1000 small files in 3.6 s against 0.76 s on the guest's own disk). Shares are exported at their host path; macOS `/var` is a symlink into `/private`, and the short spelling is kept (`$TMPDIR`, `mktemp -d` hand out `/var/folders/...`) while `/tmp` resolves to `/private/tmp`, because a share at the guest's own `/tmp` would shadow it |
| Network provider (0004) | gvproxy (gvisor-tap-vsock) via QEMU `stream` netdev; `-ssh-port`, expose API; host `podman.sock` via our own `ssh -N -L` helper (gvproxy’s `-forward-sock` kills gvproxy when guest sshd is slow to answer) | 1:1 with `podman machine`; ships with the Homebrew podman formula. The link does **not** fragment, so a UDP datagram larger than the MTU less the IPv4 and UDP headers is dropped in silence — TCP is segmented to fit and never notices. The MTU defaults to **9000**, the virtio-net jumbo frame the guest NIC already advertises and gvproxy hands out over DHCP, which puts the published-UDP ceiling at 8972 bytes instead of the 1472 a 1500-byte link allows, at no measured cost to TCP throughput (10 MB in 2.4–2.8 s at 9000 against 2.9–3.8 s at 1500). `$JM_MTU`, read at `jm start` and clamped to 576–16384, moves it; `JM_MTU=1500` is Docker's exact link size. A ceiling remains at any MTU — gvproxy does not fragment at all, so this is not Linux-style fragmentation, just a wall further out. The provider declares its MTU through `netprov.Capabilities`, and `jm doctor` prints the resulting payload ceiling per machine rather than leaving it to be discovered with a packet capture |
| Port forwarder (0004) | `jm _forwarder <name>`, detached by `jm start` (pid/log/`forwards.json` in the machine dir); desired state from `podman --connection <name> ps --format json`, triggers from `podman events` (debounced 300 ms) plus a 30 s timer; converges gvproxy’s `/services/forwarder/{expose,unexpose,all}` touching only mappings it owns | No guest agent; host port conflicts are per-mapping errors in `jm ports`/`inspect`, retried each resync. Published ports bind `0.0.0.0` by default, as `docker run -p` does on Linux; the address is a machine property (`jm init/set --publish-addr`, `$JM_PUBLISH_ADDR` folded into the record at `jm start`), not ambient state of the shell that booted the machine, so `jm inspect` and `jm ports` show what the detached forwarder is really binding. `--publish-addr` is only the *default*: a `-p` that names a host address binds that address on the Mac, as docker does, and the forwarder makes it reachable by loading its own `rdr` rules into the guest's `rdr/jm` pf anchor over SSH (ADR 0004 amendment) |
| Host resolver (0008) | `jm _resolver <name>`, detached per machine by `jm start` (pid/log/`resolver.addr` in the machine dir), bound to `127.0.0.1` on an ephemeral port and answering through Go `net.Resolver{PreferGo: false}` → libSystem/mDNSResponder; reached from the guest at gvproxy's host alias `192.168.127.254`; guest-side `local_unbound` is the port-53 hop (libc insists on 53, an unprivileged host process cannot bind it), configured as a pure forwarder with no cache; search domains from `scutil --dns` into the guest's `/etc/resolv.conf` (re-read every 30 s, pushed without a restart); aliases (`host.containers.internal`, `host.docker.internal`, the Mac's own hostname and `.local` name) from `resolver.DefaultAliases`, plus `host_containers_internal_ip` in the guest's `containers.conf.d` | gvproxy's own DNS at `192.168.127.1` is deliberately bypassed: it resolves through Go but has no notion of the Mac's own names, and jm needs A/PTR of its own (`Handler.resolve` answers PTR via `arpaToIP`) plus the loopback rewrite that turns a host `127.0.0.1` answer into the host alias (a `0.0.0.0` answer is dropped instead: it is how a hosts file blocks a name, and the host cannot reach it either). On darwin `net/cgo_unix.go` is compiled even with `CGO_ENABLED=0`, so hosts-file, scoped VPN resolvers and `.local` mDNS all apply and the release build stays pure Go; never build with `-tags netgo`, never set `GODEBUG=netdns=go`, never pass gvproxy `-config` (it silently disables every default, zones and SSH forward included). `/etc/resolv.conf` is a lossy snapshot, hence `scutil`. AAAA answers NODATA because the guest network is IPv4-only. unbound's built-in blackhole zones for the RFC 6761 TLDs (`test.`, `invalid.`, `home.arpa.`, `onion.`) are disabled with `nodefault`, or a `.test` name in `/etc/hosts` would be NXDOMAIN in a container; `localhost.` is deliberately left alone |
| Control channel (0001) | OpenSSH / `x/crypto/ssh`, root + dedicated ed25519 key | root for MVP (decided 2026-08-20); unprivileged user needs its own ADR |
| Engine API in guest | `podman system service` on `/var/run/podman/podman.sock` via our `podman_service` rc script | Ports' `podman` rc script only restarts containers |
| Guest memory (ZFS ARC) | Per-machine cap `arc_mib` (512 MiB by default, half the memory below 1024 MiB, `0` = the guest's own default), pushed by `jm start` over SSH at every start and by `jm set --arc` on a running machine: runtime `sysctl vfs.zfs.arc.max=<bytes>` plus a `vfs.zfs.arc.max="<bytes>"` line in `/boot/loader.conf` for a guest reboot jm does not see (edited with `grep`, since `sysrc(8)` refuses names with dots). OpenZFS refuses a runtime `arc.max` at or below the ARC's floor (a 32nd of the memory), so the floor `vfs.zfs.arc.min` is lowered to half the cap first when needed; it ignores a runtime `0`, so removing the cap writes the default ceiling (`arc_default_max`) back. A cap the guest still refuses is a warning, not a failed start. Default memory 2048 MiB | QEMU keeps every guest page once touched, and an uncapped ARC grows to about the guest's RAM less 1 GiB: a 12-day idle machine with no containers reached 6.92 GB in Activity Monitor, with an ARC of 3.18 GB (2026-09-13). **Rejected: `virtio-balloon`.** Measured on QEMU 11.1.1 + HVF with a 2048 MiB guest, inflating the balloon to 512 MiB dropped QEMU's RSS from about 3.1 GB to 54 MB, but its footprint stayed at 1855–1900 MB and macOS's compressed memory rose from about 0.6 GB to 3.8 GB: on macOS, `madvise(MADV_DONTNEED)` moves the pages into the compressor and does not return them. Pausing the guest with QMP `stop` keeps every page too. Capping what the guest touches bounds a running machine; an idle one gives its memory back by being suspended (0009) |
| Guest clock | `-rtc base=utc,clock=host`; guest `jm-rtcsync` reads the EFI RTC (`/dev/efi`, `EFIIOC_GET_TIME`) every 10 s and steps `settimeofday` past a 2 s threshold; `machdep.disable_rtc_set=1` in the image | The EFI RTC tracks host wall time regardless of guest drift. `disable_rtc_set=1` is mandatory — otherwise the guest writes its own skew back into the RTC and the reference is gone. No ntpd (needs internet, steps slowly); `pmset -g log` costs 2–3 s of CPU per call |
| Suspend (0009) | QEMU migration to a file (`internal/backend/qemu/suspend.go`, `internal/cli/suspend.go`, `internal/cli/resume.go`). **Suspend:** probe the guest again under the lock; journal `suspend.json` (`saving`, fsynced); stop the forwarder; the sleeper takes `podman.sock`; quiesce the guest over SSH (`sync; zpool sync; sync`, `mount -p -t p9fs` saved to `/var/run/jm-suspend.mounts`, `umount` of each 9p mount in reverse order, never `-f`); stop the `ssh -L` forward; QMP `migrate-set-capabilities` `mapped-ram`+`multifd`, `migrate-set-parameters multifd-channels=4`, `query-migrate` `blocked-reasons`; `stop`; `migrate uri=file:<dir>/suspend.state.tmp`, polled; `F_FULLFSYNC`; rename to `suspend.state`; commit the journal as `saved`; `quit`; fingerprint `disk.raw` and `efivars.fd` (size and mtime); park gvproxy; stop the resolver; the sleeper takes the SSH port. Needs the guest's memory plus 2 GiB free. **Resume:** the saved `qemu.argv` with `-M virt-<ver>` pinned (a bare `virt` is resolved through `query-machines`) and `-incoming defer`, a vanished share path swapped for an empty read-only `guest/absent/<tag>`; the same capabilities; `migrate-incoming`; wait for `paused`; delete the journal; `cont`; then one SSH script: `date -u -f %s <host epoch>`, remount (`service jm_shares start`, then any saved line still unmounted), the ARC cap if it changed, the DNS search list, `test -S` on the guest podman socket. A rejected load (`qemu.log` copied to `qemu.resume-failed.log`), `unsupported machine type`, or a changed fingerprint or hardware description discards the state and cold-boots; a launch failure or timeout keeps it | QEMU refuses to migrate with a 9p export mounted ("Migration is disabled when VirtFS export path … is mounted"), hence the unmount. Measured 2026-09-13, QEMU 11.1.1 + HVF, FreeBSD 15.1-p2, 2048 MiB guest. Save after dirtying 800 MB: **9.98 s** wall (total-time 9213 ms, downtime **19 ms**, 1132 mbps, 1.30 GB transferred), a **2.1 GB logical / 1.3 GB allocated** sparse image. Save with little dirty memory: **3.3 s**. Resume from launch: QMP 2.10 s, loaded **3.61 s**, `cont` **3.96 s**, SSH answering **4.06 s**. Footprint after restore 1452 MB. Measured 2026-09-14: the restored guest remounted its share with `mount -t p9fs` and saw a file the host wrote while it was suspended. The guest wall clock is frozen across a suspend, so the wake steps it. Rejected: `savevm` (needs qcow2; `disk.raw` is raw) |
| Wake stand-in (0009) | `jm _sleeper <name>` (`internal/sleeper`, `internal/cli/sleeper.go`), started by `jm start` for every machine whose backend and provider can suspend. It runs the suspend in-process and, while the machine is suspended, holds `podman.sock` (bound as `.jmwake` beside it, `rename(2)` over it, `SetUnlinkOnClose(false)`, closed only if the inode is still its own) and `127.0.0.1:<ssh port>` (bound once gvproxy has exited, retried for 5 s). A connection there is held unread (at most 256, each for 120 s) and, unless a `jm _wake <name>` is already running, spawns one detached (output in `wake.log`, 10 s back-off after a failed one); after the wake the sleeper splices each held connection to the real endpoint with `io.Copy`, half-close preserved. `ssh -L`'s `StreamLocalBindUnlink=yes` takes the socket back. Control socket `sleeper.sock`, one line per request: `abort`, `release-tcp <pid>`, `woke [<by> [<ms>]]`, `suspend [force]`, `status`; status in `sleeper.json`. The sleeper and its children run with every `JM_*` variable removed except `$JM_GVPROXY` | gvproxy exits when QEMU disconnects ("cannot read size from socket: EOF"), taking the SSH port and `api.sock` with it, so something else has to hold the endpoints. The wake never runs inside the sleeper, so no process ever has to stop itself. `-ssh-port -1` with API expose was considered and not adopted (unverified) |
| Idle detection (0009) | Every 15 s from `jm _sleeper` (`internal/idle`): one SSH exec on a persistent `x/crypto/ssh` connection counting `jls jid`, `sockstat -u` lines `sshd… -> /var/run/podman/po` (less 1 for the forwarder's events stream), non-sshd children of `sshd-session` from `ps -ax -o pid= -o ppid= -o comm=` (less the probe itself), and `/var/run/jm-nosleep`; plus the host `activity` file's mtime (bumped by the wrappers, `jm ssh` and a wake) and QEMU's CPU time (`ps -o time=`). Jails, the inhibit file, host activity and CPU above 25 % of one core block at once; engine clients and sessions must be seen in two samples in a row; an unreadable sample neither counts nor resets. Quiet time is capped at 30 s per sample, so a host sleep never counts down. Default 30 min (`idle_suspend_min`, 5 min to 168 h, 0 = never). Flap guard: a wake within 10 min of the suspend doubles the idle period, up to 8×; a suspension of 1 h or more resets it. Three failed automatic suspends in a row turn it off until the sleeper restarts. Guest sshd has `ClientAliveInterval 30` and `ClientAliveCountMax 4`, so a session whose client vanished ends within two minutes | `who` misses `jm ssh -- cmd`. An idle `ssh -L` holds no podman.sock connection; a `podman events` stream is exactly one `sshd-sessi` line. Measured 2026-09-14: FreeBSD `ps -o` takes everything after `=` as the header, commas included, so `-o pid=,ppid=,comm=` prints only the pid; `comm` is `sshd-session` for every session process, a pty and a non-pty command are both its children, and a tunnel's session has none. The probe fails (`sshd=0`) rather than reading idle if process titles change. The 25 % CPU threshold is **not yet calibrated** against an idle guest |
| Autostart | `jpodman`/`jdocker` (and `jm podman`/`jm docker`) start a stopped machine on demand, waiting on a blocking per-machine lock; opt out with `JM_AUTOSTART=0`, `JM_NO_AUTOSTART=1` or a leading `--no-autostart`. That is the whole mechanism: there is no login agent and no `jm autostart` command | Warm start is 12–25 s on an idle Mac, almost all of it guest boot (36.7 s measured on a loaded one). A launchd `KeepAlive` agent would loop: `jm start` is one-shot and leaves qemu, gvproxy, the forwarder, the resolver and the sleeper detached. Concurrent wrappers must wait for the lock, not fail. A **suspended** machine (0009) is woken by the wrappers, `jm start` and `jm ssh`, and by any client of `podman.sock` or the SSH port while `jm _sleeper` is alive; `JM_AUTOSTART` governs stopped machines only |
| Packaging | goreleaser + Homebrew tap `gabrielbelli/homebrew-tap`; repo `gabrielbelli/jailmachine` | decided 2026-08-20 |
| Release image verification | SHA256 sidecar only for MVP | cosign keyless post-MVP |

Known kernel-side limits (document, don't fight): no virtiofs (9p instead,
ADR 0007), no vsock.
